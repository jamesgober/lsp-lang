# lsp-lang v1.0.0 — API Freeze

**The stable release.** v1.0.0 freezes the 0.2.0 surface as the `1.x`
contract — eleven types, unchanged — and records the protocol behaviour that is
part of that contract: the lifecycle, how messages are classified, the
capabilities the server owns, encoding negotiation, position conversion, the
diagnostics mapping, document synchronization, and message ordering. Before
freezing, an adversarial review attacked the server; it found no panic on
client input and no way to desync a document, and every defect it did find is
fixed in this release.

## What is lsp-lang?

The Language Server Protocol layer of the `-lang` language-construction
family. A server built on it is a grammar and a handler: the crate owns
`Content-Length` framing, the `initialize`/`shutdown`/`exit` lifecycle,
document synchronization with incremental reparsing through
`incremental-lang`, position conversion between UTF-16 or UTF-8 columns and
byte offsets, and the translation of `diag-lang` diagnostics into protocol
diagnostics.

## What's new in 1.0.0

### The stability contract

`docs/API.md#stability` now lists what is frozen and what is not. Frozen: the
surface of every public type, the lifecycle table (which messages reach the
handler in each phase, and the error codes the server answers with), message
classification, the `positionEncoding` and `textDocumentSync` capabilities the
server owns, UTF-8-when-offered negotiation, the line-break, clamping, and
snapping rules of position conversion, the diagnostics mapping, the
document-synchronization rules, message ordering, the public dependencies
(`incremental-lang` 1, `diag-lang` 1, `serde_json` 1, `serde` 1), and MSRV
1.85. Not promised: message wording, `Debug` output, JSON key order and
whitespace, the default message limit, and performance figures.

### What the review found, and what changed

**Diagnostics on long lines are linear.** Publishing many diagnostics on one
long line in a UTF-16 session counted the line from its start for every span,
which was quadratic. `publish_diagnostics` now converts all spans in one
ascending pass before writing, so each line is counted once, in whatever
order the diagnostics come. Ten thousand scattered diagnostics on a 39 KB
non-ASCII line publish in about 2.5 ms.

**Requests need a valid id.** A request with `"id": null` was delivered to the
handler as a notification — including `shutdown`. Requests whose id is not a
string or an integer are now refused with `InvalidRequest` under a `null` id,
never dispatched and never echoed back.

**The server never answers an answer.** A malformed response from the client —
an `error` of `null`, an error object without a message or with a non-integer
code, an id with neither `result` nor `error` — used to draw an error response
from the server, which the client would read as an error for its own request
with that id. Answers are now read leniently and delivered, or logged and
dropped; nothing is sent back.

**Exactly one answer per request.** The server now tracks which of its own
requests are outstanding. `Handler::response` receives one answer for each,
whenever it arrives; a duplicate, an unsolicited id, or an answer before any
request was sent is logged instead of delivered.

```rust
fn response(&mut self, id: u64, result: Result<Json<'_>, ResponseError>, _: &mut Context<'_, G>) {
    // `id` is always one `Context::request` returned and that had no answer yet.
    if self.pending.take() == Some(id) { /* apply the answer */ }
}
```

**A grammar panic costs one document.** A panicking grammar used to unwind out
of `Server::run`. The server now catches it (where panics unwind), drops the
document, logs to the client, and calls `Handler::closed` — the same path as
an edit that cannot be applied, which `incremental-lang`'s transactional edits
make safe. A panic in the handler's own code still propagates.

**Smaller fixes.** `null` members in `InitializeParams` read as absent rather
than failing `initialize`. A message's buffer reserves at most 1 MiB before
its body arrives, so announcing a huge body no longer makes the server
allocate it up front. Client-supplied text quoted in log messages is clipped.
And the documentation now states an edit's cost precisely: its parsing work is
proportional to the edit, while moving the text after it and shifting later
line starts are linear — a `memmove` and a vectorized pass.

## Breaking changes

**None.** The public API is identical to 0.2.0. Behaviour changed only where
0.2.0 was wrong: invalid-id requests are refused instead of delivered,
malformed or unsolicited answers are logged instead of answered or delivered,
and a grammar panic drops a document instead of ending the session.

## Verification

Run on Windows x86_64 and Linux (WSL2 Ubuntu, from a sibling-free copy, as CI
checks the crate out), Rust stable and the 1.85 MSRV; the same commands run in
the configured CI matrix:

```bash
cargo fmt --all -- --check
cargo clippy --all-targets -- -D warnings
cargo clippy --all-targets --all-features -- -D warnings
cargo test
cargo test --all-features
RUSTDOCFLAGS="-D warnings" cargo doc --no-deps --all-features
cargo build --examples
cargo +1.85 test --all-features
cargo +1.85 clippy --all-targets --all-features -- -D warnings
cargo +1.85 fmt --all -- --check
cargo deny check

```

All green. Counts at this tag:

## What's next

Only additive `1.x` work, none of it committed: `serverInfo` in the
`initialize` result, `data` on `ResponseError`, documents for files the client
has not opened (for cross-file results), deferred replies from worker threads,
and UTF-32 negotiation. See `dev/ROADMAP.md`.
