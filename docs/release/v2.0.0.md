# lsp-lang v2.0.0 — Our Own Stack

**A major release.** lsp-lang 1.x depended on `serde`, `serde_json` (which its
public API re-exported) and `memchr`. 2.0 rebuilds it on the family's own
crates: [`rpc-io`](https://crates.io/crates/rpc-io) for JSON-RPC and the base
protocol's framing, [`jsonx-lib`](https://crates.io/crates/jsonx-lib) for JSON.
There are no third-party runtime dependencies left. Everything 1.x did is kept,
and the typed features a language server needs first are added: semantic tokens
(full and delta), hierarchical document symbols, go to definition, hover, and
completion, with a `$/cancelRequest` that cancels.

## What is lsp-lang?

The Language Server Protocol layer of the `-lang` language-construction family.
A server built on it is a grammar and a handler: the crate owns the transport,
the `initialize`/`shutdown`/`exit` lifecycle, document synchronization with
incremental reparsing through `incremental-lang`, position conversion between
UTF-16 or UTF-8 columns and byte offsets, cancellation, and the translation of
`diag-lang` diagnostics into protocol diagnostics. It is the language-server
engine of LexerSketch's `lsk lsp`.

## What's new in 2.0.0

### A handler declares what it offers

```rust
use lsp_lang::incremental_lang::Grammar;
use lsp_lang::{Context, Document, Features, Handler, Hover, Position, ResponseError};

struct Words;

impl<G: Grammar> Handler<G> for Words {
    fn features(&self) -> Features {
        Features::new().hover().completion(&["("])
    }

    fn hover(&mut self, doc: &Document<G>, at: Position, _: &mut Context<'_, G>)
        -> Result<Option<Hover>, ResponseError>
    {
        let offset = doc.offset(at) as usize;
        Ok(doc.text()[offset..].split_whitespace().next().map(|w| Hover::markdown(format!("`{w}`"))))
    }
}
```

The server advertises exactly the listed capabilities, reads each request, finds
the document, calls the method, and writes the answer. A request for a feature
that is not listed is `MethodNotFound`; so is a listed feature whose method was
left at its default. The list is explicit because Rust cannot see which default
methods an implementation overrode; it is built after `initialize`, so it may
depend on what the client announced.

### Typed results, hand-written JSON

`Hover`, `Location`, `CompletionItem`, `DocumentSymbol`, `SemanticTokens`,
`SemanticTokensLegend`, `TextEdit`, `Position`, and `Range` write themselves with
straight-line code (`to_json`) and the ones a handler reads read themselves with
checked accessors that say what was wrong (`from_json`, `INVALID_PARAMS`).
There are no derives, no reflection, and no macro. Results go to the wire
without ever becoming a value tree.

### Semantic tokens, full and delta

A `SemanticTokensBuilder` takes byte spans from the syntax tree in any order and
produces the protocol's delta-encoded integers: it sorts, drops overlapping and
empty tokens, converts to lines and columns in the session encoding (a surrogate
pair is two units in UTF-16), and splits a token that crosses a line break. The
server keeps the last answer per document and answers
`textDocument/semanticTokens/full/delta` with a single token-aligned edit; a
`previousResultId` it does not know is answered in full. A property test holds
the builder to a reference encoding written from the protocol's rules, in both
encodings, with CRLF, lone CR, and astral characters.

### Outlines of any depth

`DocumentSymbol` trees are written, cloned, and dropped with explicit stacks. A
200,000-level outline is serialized and freed on a 256 KiB stack in a test. The
protocol requires the selection range to lie inside the range and clients
reject the whole answer otherwise, so the server clamps it.

### Cancellation that cancels

`$/cancelRequest` now has an effect. The server queues what it reads and runs
the queue when its input has nothing more buffered, so a cancellation that
arrives with the request it names, or behind it in the same read (the usual case
for a request waiting behind slow work), is applied first: the client gets
`RequestCancelled` exactly once and the handler is never called. A handler that
is already running is **not** interrupted; the server is single-threaded, and
this is stated in the docs rather than hidden. `initialize` is the one message
that runs at once, because the transport's gate refuses what follows it until it
is answered.

### Smaller additions

`serve_stdio(grammar, handler)`, the one-call entry point; `Server::with_info`
(`serverInfo`); `Server::custom_request` and `Server::custom_notification` to
register methods outside the protocol's own; `Context::log` and `MessageType`;
`ResponseError::with_data`; `Position`/`Range` JSON conversions; re-exports of
`jsonx_lib` and `rpc_io`.

## Breaking changes

The full list and a migration table from 1.x are in the
[CHANGELOG](https://github.com/jamesgober/lsp-lang/blob/main/CHANGELOG.md#migrating-from-1x).
In short:

- `serde_json`, `Value`, and `json!` now come from `jsonx_lib`
  (`Value<'a>` borrows; `into_owned()` for `'static`).
- `Handler::initialize` returns `Result<(), ResponseError>`; capabilities come
  from `Handler::features`.
- `Handler::request`, `notification`, and `response` take `&Value` and return
  `Value<'static>`; `Json` and `Reply` are gone. The typed requests have their
  own methods, and other methods are registered with `Server::custom_request`.
- `Position` and `Range` have `to_json`/`from_json` instead of serde.
- `Context::notify`/`request` take `impl Into<rpc_io::Json>` (a `json!` value).
- Server request ids count from 1.
- `Error::InvalidHeader`, `TooLarge`, and `Json` are replaced by `Frame`,
  `Closed`, and `InvalidParams`; an oversize message is refused and the session
  goes on.
- JSON-RPC as specified: batches are answered, scalar `params` is an
  `InvalidRequest`, a client error answer without a message is an invalid
  response.

## Quality

The full local gate on Windows: `cargo fmt --all -- --check`; clippy with
`-D warnings` on the default, all-feature, and no-default-feature sets, on 1.85
and on 1.99; `cargo doc` with `-D warnings`; `cargo test` on stable and on 1.85;
`cargo bench --no-run`. Counts: 86 unit, 121 integration (65 server, 22
feature, 16 hostile-input, 12 conformance, 6 property), and 146 doctests.
The synchronization properties also ran at 30,000 cases in release.

What the new suites cover:

- **Conformance over in-memory pipes**: a whole session in order; the same
  session with bytes arriving one at a time; a message split across writes with
  pauses; 20 pipelined requests answered in order; nothing read after `exit`;
  hang-ups mid-message and before `exit` (earlier requests answered first); an
  8,000-line document; standard and unknown notifications; the server asking the
  client a question and the answer reaching the handler.
- **Hostile input**: 37 malformed or mis-typed bodies, each earning the code the
  specification prescribes under the right id with the session surviving; every
  request answered exactly once for 8 methods against 12 parameter shapes;
  absurd edit ranges; a message over the limit skipped, an announced length of
  2^62 refused unread; 1,000,000-deep JSON on a 512 KiB stack; 5,000 pipelined
  requests; 20,000 notifications; broken, duplicate, and flooded headers;
  random bytes in and out (everything written is well-framed JSON); random JSON
  scripts (one answer per request, ids only ones that were sent).
- **Properties**: position conversion in UTF-8 and UTF-16 over text with
  surrogate pairs, including positions inside a pair; the server's text and tree
  equal the client's after random edit sequences; recovery from out-of-step
  documents; the full-parse fallback; semantic tokens against a reference; the
  delta applied to the previous tokens gives the next; written symbol trees hold
  the same hierarchy.
- **Cancellation**: a request cancelled in the same read; a request cancelled
  while another runs (held in place by a channel); a cancellation for a finished
  request, an unknown id, a string id, a `null` id, or no id.

Real stdio was also driven end to end with a separate process over OS pipes
(initialize, open, tokens, hover and cancel, shutdown, exit status 0).

### Performance

`cargo bench` (Windows 11, x86_64, release, one short run; the numbers are
measurements, not guarantees):

| Benchmark | 2.0.0 |
|---|---:|
| `keystroke/1000` | ~2.8 µs |
| `keystroke/10000` | ~8.4 µs |
| `keystroke/100000` | ~116 µs |
| `request/hover` | ~1.1 µs |
| `publish/100` | ~22 µs |
| `publish/long_line_10000` | ~2.0 ms |
| `open/10000` | ~3.0 ms |
| `request/semantic_tokens` (10,000 lines, ~40,000 tokens) | ~5.9 ms |
| `request/document_symbols` (~9,000 symbols) | ~6.2 ms |
| `request/completion` (~9,000 items) | ~1.9 ms |

1.0.1 measured `keystroke/10000` at ~9.5 µs and `request/hover` at ~0.72 µs on
the same kind of machine. Hover round trips are slower in 2.0 (~1.1 µs): a
request is now received, queued, answered through a responder, and written,
which is the price of cancellation; the cost is under half a microsecond a
request. Keystrokes are a little faster. Diagnostics were ~3x slower than 1.x
until notifications the crate writes itself skipped the transport's validation
pass and copies (debug builds, tests included, still validate each); they are
now level with or faster than the figures 1.x published. There is no
controlled A/B against 1.x in the same run here.

## Known limits

- A handler that is already running cannot be cancelled (above).
- A `didChange` of N edits costs N times the document size in memory moves, as
  in 1.x; a hostile client can make a large document expensive that way.
- `rpc-io` and `jsonx-lib` are at 0.2 and their types are in this API; a breaking
  change in either before 1.0 will be absorbed by a lsp-lang major release.
- Not delivered (additive, in `dev/ROADMAP.md`): documents for unopened files,
  `Document::is_in_step`, UTF-32, `semanticTokens/range`, and the features
  LexerSketch does not need yet (references, rename, code actions, formatting).
