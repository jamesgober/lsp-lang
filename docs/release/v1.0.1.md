# lsp-lang v1.0.1 — Nothing Gets Dropped

**A robustness patch.** In 1.0.0 one failed edit dropped a document, and
language features went silent for that file until the editor reopened it; a
panic in a handler ended the whole session. 1.0.1 keeps the document and the
session in both cases, sends the `initialize` response before anything else,
bounds the server's outstanding requests, and answers a malformed request
under its own id. The public API is unchanged.

## What is lsp-lang?

The Language Server Protocol layer of the `-lang` language-construction
family. A server built on it is a grammar and a handler: the crate owns
`Content-Length` framing, the `initialize`/`shutdown`/`exit` lifecycle,
document synchronization with incremental reparsing through
`incremental-lang`, position conversion between UTF-16 or UTF-8 columns and
byte offsets, and the translation of `diag-lang` diagnostics into protocol
diagnostics.

## What's new in 1.0.1

### A failed edit keeps the document (ISSUES M74)

1.0.0 dropped a document when an edit could not be applied and called
`Handler::closed`. Every later `didChange` for it was then logged as "not
open", so hover, diagnostics, and everything else stopped for that file, with
no recovery short of closing and reopening it. Now the server works through
the failure:

1. **Incremental first, then whole.** If an edit's incremental reparse fails
   (the grammar panicked, or its lexer broke its contract, on the fragment),
   the server splices the edit into the text and parses the result from
   scratch. If that succeeds, the document is in step and `changed` is called
   as usual; a warning names the grammar fault.
2. **Out of step, not gone.** If the change cannot be applied at all, the
   document keeps its last good text, tree, and version and is marked out of
   step. That happens when an edit names a line the document does not have
   (more than one past its last), when a change of ranged edits carries a
   version no greater than the document's, when the grammar fails on the
   whole text too, or when the text would outgrow 4 GiB. Drift is logged as a
   warning, a grammar failure as an error.
3. **All or nothing.** A `didChange` whose third edit fails does not leave the
   first two applied: the document goes back to the text it started from.
4. **Recovery.** LSP has no request for the client's current text, so the
   server recovers when the client next sends it: a whole-text change is
   applied in any state and at any version (edits after it in the same
   notification apply on top of it), and a reopen replaces the document.
   Ranged changes to an out-of-step document are logged and ignored until
   then.

A failed reopen keeps the open document, out of step, instead of dropping it.
A failed first open is remembered, so a whole-text change can still open the
document.

One rule changed with it: an edit at a line more than one past the last used
to be clamped to the end of the text. Applying such an edit puts text where
the client did not, so it now takes the document out of step. The line just
past the last still means the end of the text, which is how clients write
"end of document", and a column past the end of its line is still clamped, as
the protocol prescribes. The public `Document::offset` and `Document::span`
conversions are unchanged.

### Handler panics are contained (ISSUES M75)

Only grammar code was guarded in 1.0.0. A panic in a handler's `request`,
`notification`, or `changed` unwound out of `Server::run`. Now every handler
call is guarded, where panics unwind:

| Panics in | The server |
|---|---|
| `request` | answers the request with `InternalError` (`-32603`) and the panic's message, clipped to 256 bytes |
| `initialize` | refuses `initialize` with `InternalError`; the session stays uninitialized |
| `changed`, `closed`, `notification`, `response` | logs the panic to the client as an error |

The session carries on with the same handler. Messages the handler sent before
it panicked are still sent; the handler's own state is whatever the panic
left. A document stays open through a panicking `changed`.

### The `initialize` response comes first

The protocol forbids a server to send requests or notifications before it has
answered `initialize`. In 1.0.0, anything a handler sent from
`Handler::initialize` went out before the response. Now it is held back and
written right after the response, in the order sent. If `initialize` fails,
the held-back messages are discarded, and requests among them are forgotten,
so no answer is expected for them.

### Outstanding requests are bounded

The server's own requests (`Context::request`) awaiting an answer were an
unbounded list, scanned linearly on every answer. They are now a sorted set
capped at **1024**. Sending one more cancels the oldest: the client gets
`$/cancelRequest` for it, and `Handler::response` gets `RequestCancelled`
(`-32800`) once the current handler call returns. A late answer is logged and
dropped, so every request is still answered exactly once. Settling an answer
is O(log n).

### Malformed requests keep their id

A request whose envelope does not parse, such as one whose `method` is a
number, was answered under a `null` id even when its `id` was valid, so the
client could not match the error to its request. When the message is a JSON
object with a `method` member and a string or integer `id`, the error now goes
under that id. A message without a `method` may be a broken answer to one of
the server's own requests, and is still never answered under its id.

## Breaking changes

**None in the API.** No public item was added, removed, or changed. The
behaviour changes are the fixes above. `docs/API.md#stability` recorded two of
them as contract in 1.0.0 (dropping a document whose edit fails, and handler
output preceding the `initialize` response). Both were defects, and the
stability section now records the 1.0.1 behaviour. A handler that relied on
`closed` being called after a failed edit no longer gets that call; the
document stays open.

## Verification

Run on Windows x86_64, Rust stable and the 1.85 MSRV:

```bash
cargo fmt --all -- --check
cargo clippy --all-targets -- -D warnings
cargo clippy --all-targets --all-features -- -D warnings
cargo clippy --all-targets --no-default-features -- -D warnings
RUSTDOCFLAGS="-D warnings" cargo doc --no-deps --all-features
cargo +1.85 clippy --all-targets --all-features -- -D warnings
cargo test --all-features
cargo test --no-default-features
cargo +1.85 test --all-features
cargo bench --no-run
```

All green. Counts: 65 unit, 57 integration, 4 property, and 116 doctests.
New tests cover each fix: a handler that panics in each of its six entry
points, `initialize` ordering on success and failure, the request cap and a
late answer to a cancelled request, malformed requests with valid and invalid
ids, out-of-range lines, repeated versions, rollback of a partly applied
change, the full-reparse fallback, failed opens and reopens, and recovery by
whole-text change. Two new properties: the server never reports a text the
client did not have at that version, under random out-of-range edits and
repeated versions, and it recovers on the next whole-text change; and with a
grammar whose fragment reparse always panics, the full-reparse fallback still
tracks the client's text exactly. Both were run at 20,000 cases.

The keystroke and hover benchmarks match 1.0.0 (`keystroke/10000` ~9.5 µs,
`request/hover` ~0.72 µs on Windows): the guards are `catch_unwind` calls,
which cost nothing until a panic.
