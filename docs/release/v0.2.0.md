# lsp-lang v0.2.0 — The Language Server Core

**The core, and the hard part of the roadmap.** v0.2.0 turns the scaffold into
a working language-server framework. A server built on lsp-lang is a grammar
and a handler: the crate owns the protocol — `Content-Length` framing, the
`initialize`/`shutdown`/`exit` lifecycle, document synchronization with
incremental reparsing, position conversion between UTF-16 columns and byte
offsets, and the translation of `diag-lang` diagnostics into protocol
diagnostics. The surface is eleven types; the hot path builds no JSON value
trees.

## What is lsp-lang?

The Language Server Protocol layer of the `-lang` language-construction
family. Everything a language server needs that is not about the language
itself lives here, so the code a language writes is its grammar — an
`incremental-lang` grammar, which parses each open document and reparses only
the node around each edit — and a handler, which answers the requests the
language supports and publishes diagnostics. It is one of the FEAT-tier crates
of the family, built on `incremental-lang` and `diag-lang`.

## What's new in 0.2.0

### `Server` — the protocol, owned

`Server::run` serves one session over any `BufRead` and `Write`: stdin and
stdout for an editor, a socket, or a buffer in a test. It reads framed
messages, enforces the lifecycle — requests before `initialize` are refused
with `ServerNotInitialized`, requests after `shutdown` with `InvalidRequest`,
and notifications outside the session window are dropped — and returns
`Ok(())` for a clean `shutdown` then `exit`, or an `Error` that maps to the
protocol's non-zero exit.

```rust
let mut server = Server::new(MyGrammar, MyHandler);
match server.run(io::stdin().lock(), io::stdout().lock()) {
    Ok(()) => ExitCode::SUCCESS,
    Err(err) => {
        eprintln!("language server stopped: {err}");
        ExitCode::FAILURE
    }
}
```

Malformed JSON is answered with `ParseError` and messages of the wrong shape
with `InvalidRequest`, and the session continues. Only a broken transport,
broken framing, a message over the configurable size limit, or the end of the
session stops `run`.

### `Handler` — a language in one trait

Six methods, every one defaulted, so a handler implements only what its
language supports: `initialize` returns capabilities (merged with the
server's `positionEncoding` and `textDocumentSync`), `changed` runs after a
document opens or changes, `closed` after it closes (by default clearing its
diagnostics), and `request`, `notification`, and `response` receive
everything else.

```rust
impl Handler<Lisp> for LispServer {
    fn changed(&mut self, doc: &Document<Lisp>, cx: &mut Context<'_, Lisp>) {
        let analysis = analyze(doc.text(), doc.tree());
        cx.publish_diagnostics(doc, &analysis.diagnostics);
    }

    fn request(&mut self, method: &str, params: Json<'_>, cx: &mut Context<'_, Lisp>)
        -> Result<Reply, ResponseError>
    {
        match method {
            "textDocument/hover" => {
                let p: PositionParams<'_> = params.parse()?;
                // look up `p.position` in the document, reply with a range…
            }
            _ => Err(ResponseError::new(ResponseError::METHOD_NOT_FOUND, method)),
        }
    }
}
```

### `Document` — incremental sync and position conversion

Every open file is an `incremental_lang::Document` plus a line index. A
`didChange` edit is converted from its protocol range to a byte span, applied,
reparsed incrementally, and folded into the line index in place — only the
line starts whose deciding bytes the edit touched are rescanned, and the rest
shift in one vectorized pass. `position`, `offset`, `range`, and `span`
convert in the session encoding, negotiated at `initialize`: UTF-8 when the
client offers it (byte columns convert without scanning), UTF-16 otherwise.
Line breaks are `\n`, `\r\n`, and lone `\r`; out-of-range positions are
clamped as the protocol prescribes; a column between the halves of a
surrogate pair snaps to its character. Conversions are total.

An edit that cannot be applied (the grammar's lexer broke its contract, or
the text outgrew 4 GiB) drops the document rather than serve positions for
text the client no longer has, and the client is told why through
`window/logMessage`.

### `Context` — the channel back to the client

`publish_diagnostics` converts `diag_lang::Diagnostic`s to protocol
diagnostics and writes them to the wire field by field: the primary label
becomes the range, severities map to Error, Warning, Information, and Hint,
the primary label's text, notes, and help lines join the message, and
secondary labels become related information. `notify` and `request` send any
`Serialize` value; server-to-client requests get numbered ids, and the
client's answers come back through `Handler::response`. Documents borrowed
from a context live for the whole call, so a handler can hold one while it
publishes.

### `Json`, `Reply`, `ResponseError` — no value trees

The JSON-RPC envelope is parsed in place: method names and URIs are borrowed
from the message, and parameters stay raw JSON until the handler calls
`Json::parse` with the type it wants — a borrowing struct, a `Position`, or a
`Value`. A mismatch becomes `InvalidParams`, ready for `?`. Results are
serialized straight to text in a `Reply`, which the server copies into the
response envelope verbatim. `ResponseError` carries the protocol's error codes
as constants.

### Examples, tests, and benchmarks

Three runnable examples — `server` (a Lisp language server with live
diagnostics, hover, and go-to-definition; `--stdio` serves a real editor),
`encodings` (the same hover asked by a UTF-16 and a UTF-8 client), and
`client_requests` (`workspace/configuration` and its answer) — share a
complete language server in `examples/common`, written as the template for
wiring in a real language. Its name resolution uses `symbol-lang`, whose
diagnostics publish with no adapter.

The integration tests drive the server through byte streams as an editor
would: lifecycle, framing, every error response, document sync in both
encodings, diagnostics, and server-to-client requests. The property tests
check, for arbitrary edit sequences in both encodings — including CRLF and
lone CR line breaks, multi-byte characters, surrogate pairs, whole-text
replacements, and several edits per notification — that the server's text
always equals an independent client-side model, that the tree always equals a
fresh parse, that every position round-trips, and that published diagnostics
are well-formed. A soak run of 20,000 cases per property found no divergence.

### Dependency wiring

`incremental-lang` 1 and `diag-lang` 1 are wired, and re-exported along with
`serde_json` so a server needs one dependency. `serde_json` (with
`raw_value`), `serde`, and `memchr` are added for the wire format and SIMD line
scanning. `symbol-lang` is deliberately not wired: its scope table is a tool a
resolver threads through its own walk, and the place it meets the protocol is
its diagnostics, which publish as-is. The reasoning is recorded in
`dev/ROADMAP.md` under the anti-deferral rule. The crate is `std`-only; the
scaffold's `std` and `serde` features and `loom` dev-dependency were removed.

### Scaffold fixes

`Cargo.toml` had unquoted `keywords` and `categories`, so the manifest did not
parse; `clippy.toml` declared MSRV 1.87 against the crate's 1.85; `deny.toml`
named another project; two docs carried byte-order marks; and the README
linked a `dev/DIRECTIVES.md` that does not exist. All are fixed.

## Breaking changes

**None.** v0.1.0 exposed no public API; everything in 0.2.0 is new surface. The
removed `std` and `serde` features had no code behind them.

## Verification

Run on Windows x86_64 and Linux (WSL2 Ubuntu, from a sibling-free copy, as CI
checks the crate out), Rust stable and the 1.85 MSRV; the same commands run in
the configured CI matrix:

```bash
cargo fmt --all -- --check
cargo clippy --all-targets -- -D warnings
cargo clippy --all-targets --all-features -- -D warnings
cargo test
cargo test --all-features
RUSTDOCFLAGS="-D warnings" cargo doc --no-deps --all-features
cargo build --examples
cargo +1.85 test --all-features
cargo +1.85 clippy --all-targets --all-features -- -D warnings
cargo +1.85 fmt --all -- --check
cargo deny check
cargo audit
```

All green. Counts at this tag:

- 49 unit + 41 integration + 2 property + 116 doctests. The doctests include
  every `rust` example in `README.md` and `docs/API.md`, wired into
  `cargo test` so the published examples cannot drift from the API.

Benchmark baselines (x86_64, release profile; measured end to end through
`Server::run`, timing only the measured messages; documents are generated
Lisp at about 34 bytes per line):

| Benchmark | Windows | Linux (WSL2) |
|---|---:|---:|
| `keystroke/1000` (one `didChange`) | ~2.3 µs | ~1.4 µs |
| `keystroke/10000` | ~10 µs | ~6.4 µs |
| `keystroke/100000` (3.4 MB document) | ~137 µs | ~61 µs |
| `request/hover` (round trip) | ~0.74 µs | ~0.44 µs |
| `publish/10` (keystroke + 10 diagnostics) | ~13 µs | ~8.5 µs |
| `publish/100` (keystroke + 100 diagnostics) | ~36 µs | ~26 µs |
| `open/1000` | ~0.34 ms | ~0.19 ms |
| `open/10000` | ~3.1 ms | ~2.1 ms |
| `open/100000` | ~57 ms | ~23 ms |

A keystroke in a very large file is dominated by `incremental-lang`'s reparse
and the splice of its contiguous text; lsp-lang's own share — reading the
message, converting the range, patching the line index — stays a small
fraction.
